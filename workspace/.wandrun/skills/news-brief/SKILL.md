# 资讯简报

一期简报分四个阶段。**每个阶段结束都停下来等用户确认**，用户没确认前不要进入下一阶段；
用户要求修改时留在当前阶段修改后再请确认。每次回复开头用 `Steps` 显示四个阶段的状态。

| 阶段 | 产出 | 用户确认方式 |
| --- | --- | --- |
| 1 选题 | 渠道总览 + 候选清单 | 在 `MultiSelect` 勾选并提交 |
| 2 调研 | 每条的核实事实与素材 | 回复“可以”或指出修改 |
| 3 成稿 | `brief.json` → HTML，在浏览器打开给用户看 | 用户在浏览器画面里看完后确认 |
| 4 发布 | 逐页 PNG + 小红书标题、正文、标签 | 用户确认文案后发布 |

所有文件写在当前对话目录的 `brief/` 下（相对路径即可）。

## 阶段 1：渠道总览与选题

1. 时间窗默认“今天 0 点（用户时区）到现在”，换算成 UTC 调用 Reader。
2. 全量取数，不要只看一个来源：
   - `get_subscription_updates_summary`：各分组、各订阅的更新数；
   - `list_ranking_snapshot`：`hacker_news`、`github`、`techtwitter` 三个榜各取第一页；
   - 更新数 > 0 的订阅用 `list_subscription_updates` 读标题和链接（单个订阅最多 2 页）。
3. 去重合并同一事件（同一链接或同一主题在多个渠道出现），**多渠道同时出现是重要信号**。
4. 选 6～10 条候选。优先：新发布的产品/模型/开源项目、有具体数字的进展、多个渠道同时讨论、
   对开发者或 AI 从业者有直接影响。排除：纯观点帖、旧闻再传播、无法找到一手来源的传闻。

回复结构（一个 `wandrun-ui` 块，文字说明放在块外，两三句即可）：

- `Metrics`：扫描总条数、渠道数、去重后事件数、候选数；
- `BarChart`：各渠道的条数，**按来源类型拆开**，不要把全部订阅合成一根柱子：订阅按 `source_kind` 汇总（YouTube、X 账号、Reddit、RSS、网页），
  热榜单独列（HN 热榜、GitHub 趋势、X 热榜，写实际读取的条数）；**最多 6 根**，按条数从多到少排列，条数最少的类型合并为“其他”；
  手机上柱子窄，**标签用短名，不超过 4 个汉字宽**（如“网页”“Reddit”“X”“HN”“GitHub”“YouTube”“其他”），口径写进 `title`；
- `Tabs`：按渠道分 2～5 个标签页（如 HN / GitHub / X / 订阅），每页一个 `Table`，列为
  `#`、标题（译成中文，≤ 30 字）、热度（分数/星标/条数），最多 8 行；
- `Card` 内放 `MultiSelect`（`variant: "checklist"`，`stateKey: "picks"`，每项 `note` 写一句入选理由
  和来源渠道）+ `TextInput`（`stateKey: "note"`，可选补充）+ `Submit`（“按这些做简报”）。

用户提交后，提交内容会作为下一条消息回来；以其中的选择为准，最终 3～6 条。

## 阶段 2：调研与事实素材

对每条入选内容：

- 读一手来源（官方博客、仓库 README/Release、论文摘要页、原帖）。Reader 只给标题和链接，
  内容要靠搜索或读取原文获得。有协作 Agent 时，**每条委派一个检索任务并行进行**，
  说明要核实什么、需要哪些数字。
- 每条整理：一句话说清是什么；2～3 个**带出处的具体数字**（分数、价格、星标、版本、日期）；
  3 个要点；为什么值得关注（对读者的影响，不复述新闻）；一手链接。
- 区分事实与说法：厂商自报的指标写“官方称”，榜单写“截至何时”，未核实的不写进简报。

回复：每条一个 `Card`，内含 `KeyValue`（是什么 / 关键数字 / 来源可信度）、`List`（要点）、
`Source`（一手链接）；最后一个 `Callout` 列出核实中发现的问题（如数字口径不一致、只有二手来源）。
请用户确认或修改。

## 阶段 3：成稿与浏览器预览

1. 按下面的结构写 `brief/brief.json`。**只写内容，不改版式**；版式由模板统一负责。
2. 运行：`python3 <技能目录>/scripts/render.py brief/brief.json brief --html-only`
   - 退出码 1 会说明哪一页、哪个字段超长或溢出，按提示改短后重跑，直到通过；
   - 不要通过缩小字号或删模板样式来“解决”溢出。
3. 用浏览器打开预览给用户看：`agent-browser --cdp "$WANDRUN_BROWSER_CDP" open "file://<brief.html 的绝对路径>"`。
   告诉用户在聊天里的浏览器卡片中查看（整份简报竖排，可滚动），并说明一共几页、每页讲什么。
   用户确认前保持页面打开，修改后重新渲染并 `reload`。

`brief.json` 字段（字数按显示宽度计，汉字 1、英文 0.55；脚本会检查；示例中的 `//` 注释只作说明，实际文件必须是合法 JSON）：

```json
{
  "masthead": "AI 情报站",              // 刊名，固定
  "issue": "No.12",                    // 期号
  "date_label": "2026.10.20 · 周二",
  "brand": "Wandrun",                  // 页脚署名
  "headline": "今天最值得看的 **4** 件事", // 封面主标题 ≤ 22，**…** 为强调色
  "stats": {"scanned": 93, "channels": 6, "picked": 4},
  "channels": [{"name": "Hacker News", "count": 30}],   // 封面底部渠道胶囊，与阶段 1 一致
  "stories": [{
    "tag": "开源",                     // ≤ 6：开源 / 模型 / 产品 / 安全 / 论文 / 工具 / 行业
    "channel": "Hacker News #1",       // 从哪个渠道发现
    "title": "DeepSeek 开源推理引擎 **DeepInfer**",  // ≤ 40
    "short_title": "DeepSeek 开源推理引擎",           // ≤ 18，封面目录用
    "summary": "一句话说明发生了什么",   // ≤ 90
    "facts": [{"value": "473", "label": "HN 得分"}], // 0～3 个；value 只放数字或极短词（3 个时 ≤ 7 字宽）
    "points": ["要点，可用 **强调**"],   // ≤ 4 条，每条 ≤ 48
    "why": "对读者意味着什么",           // ≤ 80
    "source": "github.com/deepseek-ai/DeepInfer",   // 页脚显示的短来源
    "url": "https://github.com/deepseek-ai/DeepInfer"
  }],
  "ending": {"title": "今天就到这里", "note": "…", "made": "这份简报由 **Wandrun** 的 Agent …"}
}
```

写作标准：标题说清“谁做了什么”，不用“重磅”“炸裂”；数字必须来自阶段 2 的来源；
强调色每页最多两处；中英文之间加空格。

## 阶段 4：出图与发布

1. 运行 `python3 <技能目录>/scripts/render.py brief/brief.json brief`，得到 `brief/page-01.png` …；
   用 `read_file` 抽看封面和任一正文页，确认没有错字、截断或空白页。
2. 写小红书文案：标题 ≤ 20 字（如“10.20 AI 情报｜DeepSeek 开源推理引擎”）；正文 150～300 字，
   每条一行“序号 + 一句话 + 关键数字”，结尾提示“原始链接见最后一页”；3～5 个标签（不带 #）。
3. 回复用户：`Gallery` 展示全部页面（附件路径即 `brief/page-XX.png`，消息同时附上这些图片），
   `KeyValue` 展示标题、标签、可见范围；正文放在块外。请用户确认。
4. 用户确认后才调用发布工具，可见范围按用户要求（未说明时问一句）。发布工具若运行在容器里，
   图片必须是它能读到的路径，见所在 Agent 的部署说明。
5. 发布可能耗时数分钟。工具报错或连接断开时**不要重试发布**，先用查询自己笔记的工具确认是否已发布，
   再如实告诉用户结果。
